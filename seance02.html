3e Année Sciences de l'Informatique (STI) Module : Bases de Données — Séance 2 (2 heures)

Liens entre Entités (1-N, N-N) et Passage au Modèle Relationnel

Objectifs : Identifier les liens entre entités, transformer un problème en schéma relationnel (tables, clés primaires et étrangères) et garantir l'intégrité référentielle.

Scénario pédagogique calibré (120 minutes)

1. Accroche : Pourquoi ne pas tout mettre dans un seul tableau ? 15 min

Avant d'utiliser un SGBD, le gérant de Pixel Zone enregistrait chaque partie jouée dans une seule feuille Excel :

numSess dateSess dureeH numInscr pseudo tel codePoste typePoste tarifH
201 2026-11-10 2 101 Ghost_TN 22114455 P01 PC Gamer RTX 8.000
202 2026-11-10 1 102 Nova_99 55889900 P02 PlayStation 5 10.000
203 2026-11-12 3 101 Ghost_TN 22114400 P02 PlayStation 5 10.000
204 2026-11-15 1 101 Ghost_TN 22114455 P03 Casque VR 15.000
  1. Quel problème constatez-vous sur le numéro de téléphone de Ghost_TN ?
  2. Si le gérant supprime la session 204 (annulée), quelle information sur la salle est définitivement perdue ?
  3. Comment stocker ces informations séparément tout en sachant quel joueur a joué sur quel poste ?
Corrigé — Limites du tableau unique
  • Redondance & incohérence : Les infos de Ghost_TN sont répétées 3 fois avec deux téléphones différents (22114455 et 22114400).
  • Anomalie de suppression : Effacer la session 204 fait disparaître l'unique trace du poste P03 (Casque VR) et de son tarif.
  • Solution relationnelle : Séparer les données en plusieurs tables distinctes et les relier grâce à leurs identifiants (clés primaires et clés étrangères).

2. Activité de découverte : Relier les entités de « Pixel Zone » 30 min

En séance 1, nous avons identifié trois entités : Joueur (numInscr), Poste (codePoste) et Jeu (codeJeu). Le gérant ajoute maintenant les règles de gestion suivantes :

  • Règle 1 (Sessions) : Une Session de jeu est identifiée par un numéro (numSess), possède une date (dateSess) et une durée en heures (dureeH). Un Joueur peut effectuer plusieurs sessions, mais chaque session est réservée par un seul joueur.
  • Règle 2 (Affectation) : Un Poste accueille plusieurs sessions au fil du temps, mais chaque session se déroule sur un seul poste.
  • Règle 3 (Jeux installés) : Un Poste peut contenir plusieurs jeux installés, et un même Jeu peut être installé sur plusieurs postes. Pour chaque installation, le gérant veut mémoriser la date d'installation (dateInstall).
  1. Analyser les liens : Indiquez le type de lien (1-N ou N-N) pour chacune des trois relations :
    • Entre Joueur et Session : __________________
    • Entre Poste et Session : __________________
    • Entre Poste et Jeu : __________________
  2. Placer les clés étrangères (liens 1-N) : Pour savoir quel joueur a fait la session 201, faut-il ajouter numSess dans la table Joueur, ou numInscr dans la table Session ? Justifiez. Faites de même pour le lien entre Poste et Session.
  3. Gérer le lien N-N : Peut-on simplement ajouter une colonne codeJeu dans la table Poste si un PC contient 15 jeux ? Quelle solution permet de stocker toutes les installations et leur dateInstall ?
  4. Écrire le schéma relationnel : Donnez la représentation textuelle complète des 5 tables de la base Pixel Zone en notant #clePrimaire et cleEtrangere#.
Corrigé — Modèle relationnel Pixel Zone

1. Types de liens : Joueur–Session (1-N) ; Poste–Session (1-N) ; Poste–Jeu (N-N).

2. Placement des clés étrangères (1-N) : On place toujours la clé du côté 1 dans la table du côté N. Un joueur pouvant avoir des dizaines de sessions, on ne peut pas mettre numSess dans Joueur (sinon on violerait l'atomicité). On ajoute donc numInscr# et codePoste# dans Session.

3. Décomposition du lien N-N : Impossible de mettre 15 codes de jeux dans une seule cellule de Poste. On crée une table d'association Installation contenant les deux clés étrangères (formant ensemble la clé primaire composée) ainsi que l'attribut porté dateInstall.

4. Représentation textuelle des 5 tables :

Joueur (#numInscr, pseudo, dateNaiss, tel)
Poste (#codePoste, typePoste, tarifH, etat)
Jeu (#codeJeu, titre, genre, ageMin)
Session (#numSess, dateSess, dureeH, numInscr#, codePoste#)
Installation (#codePoste#, #codeJeu#, dateInstall)

3. Synthèse : Le Modèle Relationnel et ses Règles 15 min — Trace écrite

A. Correspondance du vocabulaire

Niveau conceptuel (Séance 1) Niveau relationnel (Tables SQL) Exemple (Pixel Zone)
Entité Table (ou Relation) Joueur, Poste
Attribut Champ (ou Colonne) pseudo, tarifH
Occurrence Enregistrement (Ligne / Tuple) (101, 'Ghost_TN', '2009-04-12', '22114455')
Identifiant Clé primaire (PK) — notée #champ ou soulignée #numInscr, #codePoste
Lien vers une autre table Clé étrangère (FK) — notée champ# numInscr# dans Session

B. Les deux règles d'or de passage au modèle relationnel

Figure 2.1 — Les 2 règles d'or de transformation du modèle Entité-Association en Schéma Relationnel.
  • Lien 1-N (Un-à-Plusieurs) : La clé primaire de la table côté 1 (table mère) migre comme clé étrangère dans la table côté N (table fille).
  • Lien N-N (Plusieurs-à-Plusieurs) : On crée une nouvelle table d'association dont la clé primaire est composée des clés primaires des deux tables reliées (qui sont aussi clés étrangères), accompagnée des éventuels attributs propres au lien.

C. Les 3 contraintes d'intégrité

  • Intégrité de domaine : Chaque valeur saisie doit respecter le type et les bornes autorisées (ex. : dureeH > 0).
  • Intégrité d'entité : Toute table possède une clé primaire unique et non nulle.
  • Intégrité référentielle : Toute valeur d'une clé étrangère doit obligatoirement exister dans la clé primaire de la table mère (impossible d'enregistrer une session pour un joueur 999 qui n'existe pas dans Joueur).

4. Atelier « Chasse aux erreurs » : Diagnostiquer un schéma 20 min

Erreur 1 — Sens de la clé étrangère inversé

Dans un lycée, un Élève appartient à une seule Classe, et une Classe contient plusieurs élèves. Un étudiant propose :

Classe (#codeCl, niveau, numEleve#)
Eleve (#numEleve, nom, prenom)

Question : Pourquoi cette conception bloque-t-elle dès le deuxième élève d'une classe ? Proposez la correction.

Corrigé — Erreur 1 La clé étrangère a été placée du mauvais côté (côté 1 au lieu du côté N). Une ligne de Classe ne peut stocker qu'un seul numEleve. Correction :
Classe(#codeCl, niveau) et Eleve(#numEleve, nom, prenom, codeCl#).

Erreur 2 — Violation d'intégrité référentielle

On dispose de la table mère Joueur contenant uniquement les numéros 101, 102 et 103, et de la table fille Session ci-dessous. Repérez les 2 anomalies d'intégrité :

#numSess dateSess dureeH numInscr# codePoste#
301 2026-11-18 2 101 P01
302 2026-11-18 1 109 P02
301 2026-11-19 3 102 P01
Corrigé — Erreur 2
  • Ligne 2 (numInscr = 109) : Violation d'intégrité référentielle (le joueur 109 n'existe pas dans la table mère Joueur).
  • Ligne 3 (numSess = 301) : Violation d'intégrité d'entité (doublon sur la clé primaire 301 déjà utilisée en ligne 1).

Erreur 3 — Oubli de table d'association

Dans une clinique, un Médecin soigne plusieurs Patients et un Patient peut consulter plusieurs Médecins à différentes dates. Peut-on relier directement ces deux tables sans créer de troisième table ?

Corrigé — Erreur 3 Non. C'est une relation N-N. Il faut créer une table d'association, par exemple : Consultation(#idMed#, #idPat#, #dateCons, diagnostic) (ou avec un identifiant propre #numCons si un patient peut voir le même médecin plusieurs fois).

5. Application en autonomie : Conception du Fil Rouge « TechStore » 25 min (15 min binôme + 10 min correction)

Note : Cette base de données servira de fil rouge pour tous nos travaux pratiques SQL des séances 3 à 9.

La boutique de matériel informatique TechStore souhaite informatiser la gestion de ses ventes selon les règles suivantes :
  • Chaque Client est identifié par un numéro (idClt) et possède un nom, un prénom, une ville, un téléphone (facultatif) et une date d'inscription (dateInscr).
  • Chaque Produit possède une référence unique (refProd), une désignation, une catégorie, un prix unitaire (prixUnit) et une quantité en stock (qteStock).
  • Une Commande est identifiée par un numéro (numCmd) et comporte une date (dateCmd). Un client peut passer plusieurs commandes, mais chaque commande appartient à un seul client.
  • Une Commande peut porter sur plusieurs produits, et un même Produit peut figurer dans plusieurs commandes. Pour chaque produit commandé dans une commande, on doit enregistrer la quantité commandée (qteCmd).
  1. Identifiez les 3 entités de base et leurs identifiants.
  2. Précisez le type de lien (1-N ou N-N) entre Client et Commande, puis entre Commande et Produit.
  3. Écrivez la représentation textuelle complète des 4 tables du modèle relationnel (en nommant la table d'association LigneCommande).
  4. Dans quel ordre faudra-t-il créer ces tables en SQL à la séance 3 pour respecter l'intégrité référentielle ?
Corrigé — Schéma du Fil Rouge TechStore (boutique_info)

1. Entités de base : Client (idClt), Produit (refProd), Commande (numCmd).

2. Liens : Client — Commande : 1-N | Commande — Produit : N-N (avec attribut porté qteCmd).

3. Modèle relationnel (4 tables) :

Client (#idClt, nom, prenom, ville, tel, dateInscr)
Produit (#refProd, designation, categorie, prixUnit, qteStock)
Commande (#numCmd, dateCmd, idClt#)
LigneCommande (#numCmd#, #refProd#, qteCmd)

4. Ordre de création / peuplement : D'abord les tables mères indépendantes (Client et Produit), puis Commande (qui référence Client), et enfin LigneCommande (qui référence Commande et Produit).

6. Quiz éclair de clôture 15 min

1. Vrai ou Faux : « Dans une relation 1-N, la clé étrangère est toujours placée dans la table du côté 1. »
Réponse : Faux — Elle migre toujours du côté 1 vers la table du côté N (table fille).
2. Vrai ou Faux : « Une clé étrangère peut apparaître plusieurs fois avec la même valeur dans une table fille. »
Réponse : Vrai — Par exemple, un même client (idClt = 1) peut apparaître dans plusieurs lignes de la table Commande.
3. Structure : Dans la table LigneCommande(#numCmd#, #refProd#, qteCmd), pourquoi la clé primaire est-elle composée de deux champs ?
Réponse : Parce qu'une même commande contient plusieurs produits différents, et un même produit apparaît dans plusieurs commandes. Seul le couple (numCmd, refProd) identifie une ligne de manière unique.
4. Intégrité : Peut-on supprimer un Client de la base s'il possède encore des commandes enregistrées dans la table Commande ?
Réponse : Non (par défaut en mode RESTRICT), car cela laisserait des commandes « orphelines » pointant vers un client inexistant (violation de l'intégrité référentielle).
5. Vocabulaire : Quel terme du modèle relationnel correspond à une « ligne » d'une table ?
Réponse : Un enregistrement (ou tuple).
